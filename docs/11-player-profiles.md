# 11 — Player profiles (the people in the footage)

Added 2026-08-21. A Dixie club player asked for a club-wide leaderboard /
profile system, and the Discord thread put it sharper: "if you know you're
going to play against one of these players, is there something your system
might be able to tell you beforehand?" This is the first step — one profile
per named player, built from every clip they were tagged on, on the website.

Not to be confused with `/profile` (`web/src/pages/Profile.tsx`), which is the
signed-in user's OWN coaching profile that the AI coach reads.

## Shape

```
read-out (/analyze, /library) ── "Name this player" on Player A / Player B
        │                                   │
        │ summarizeClip(analysis, side)     │ players + player_clips (Supabase, RLS)
        ▼                                   ▼
   ClipSummary (a few KB: shots, placement, coverage, T-time,
   predictability, shot classes, cell→cell transitions, opponent's numbers)
        │
        ▼
   /players/:id ── buildProfileStats(clips) → stats, scoutingNotes(stats), calendarWeeks(clips)
```

- The **analysis itself never moves.** It stays where it always was — in the
  browser that ran it (`web/src/analysis/history.ts`), footage and pose track
  included. A tag stores only the summary, so a profile is readable from any
  machine without ever uploading a match video anywhere new.
- **Everything is the user's own.** `players` and `player_clips` carry
  `user_id`, and every policy is `auth.uid() = user_id` (authenticated role
  only). Rosters are private to whoever built them; club-wide sharing is a
  later, deliberate step, not an accident waiting to happen.
- **Predictability is pooled the pipeline's way.** The per-clip score is
  `1 − H/Hmax` over the player's cell-to-next-cell transition matrix
  (`entropy_predictability` in `analysis/analyze.py`). The profile sums the
  transition matrices across clips and runs the same formula
  (`predictabilityFromTransitions`), so a profile's score means exactly what a
  single read-out's does — it is not an average of scores. T-time and coverage
  are time-weighted; rally length is rally-weighted; placement and shot mix are
  sums.

## What the profile claims, and on what

The product's rule everywhere else applies here with extra force, because a
profile is read as a verdict on a person:

- **Measured from position and timing** (solid): coverage, time within 1.5 m
  of the T, which court cell a shot went to ("placement" — the pipeline's
  retrieval proxy: the opponent's position when they played the next ball,
  standing in for where the shot landed, because there is no ball tracking),
  the cell-to-cell patterns and the predictability score, rally lengths.
  Shot *detection* was audited at ~63% precision on club footage, so counts
  carry some phantom shots and misses.
- **Indicative only**: the shot classes (drive / cross-court / drop / boast /
  volley) — read from body pose alone and never audited.

Every scouting note carries a basis chip saying which of the two it rests on,
and the notes stay silent under 40 of the player's own shots (30 classified
shots for the class-based ones) rather than extrapolate. The thresholds live
in `scoutingNotes` in one place, each with the number the sentence rests on in
the sentence, so a reader can disagree with the adjective and keep the
measurement.

## The recordings grid

The GitHub-contributions idea from the thread: one cell per day over the last
52 weeks, a recording lights its day, more recordings on a day = a darker
cell, and each cell's tooltip lists the recordings. Levels are relative to the
busiest day so a profile with four recordings still lights up; the grid
scrolls inside its own container on a phone rather than widening the page.

## Clicking a day, and the movement chart

Every cell in the recordings calendar is a button: click it and a panel under
the grid lists that day's recordings (title, which side, duration, shots,
T-time, predictability), with "Open in library" when the clip is on this
browser and "Show in list", which scrolls to and highlights the row in the
recordings list. Only days with recordings are tab stops; the selected day is
outlined in the ink accent; Escape closes the panel. On iOS a tapped cell opens
the same panel in the same card.

"Court movement across recordings" (`movementProfile` in
`src/features/players/aggregate.ts`) reads each clip's coverage heatmap and
splits the player's time into depth thirds (front / middle / back — row 0 of
the heatmap is the front wall, so the bars draw front at the top, like the
court plan) and width bands (left / centre / right, 3-2-3 on the 8-column
grid), plus "spread" — the share of court cells holding at least a tenth of
the busiest cell's time. One stacked bar per recording, chronological, then a
time-weighted "All" bar. All of it is position-based — measured, not inferred.

## The recordings feed, and "Show detailed analysis"

The bottom of a profile is a feed of the recordings, newest first, each card
led by a picture — a **still from the footage** when the clip was tagged in
the browser that had the video (one JPEG, captured there at tag time, ~15–40
KB), or a **data-drawn poster** (the court plan) when it was tagged from a
saved match with no footage. The promise holds: the video itself never leaves
the machine that ran the analysis; what travels is one frame and the read-out's
numbers. At tag time the browser also stores the full analysis with the pose
track stripped (`analysisForStorage`, ~15–40 KB JSON). Both live in the public
Supabase Storage bucket `profile-media` under `<uid>/<clip id>/…` — anyone can
read (a shared profile needs them without a session; the paths are uuids),
only the owner can write, and only inside their own folder
(`storage.objects` policies at the bottom of `supabase/schema.sql`).

"Show detailed analysis" opens the full read-out: `/library?match=<id>` when
the clip is in this browser's library; otherwise `/players/:id/clips/:clipId`
(or the sample / shared equivalents) renders `ResultsView` from the stored
analysis with the still where the video would be and a caption that says so.
Clips tagged before this existed show "Numbers only". The bundled sample's
posters and analyses are committed under `web/public/sample/clips/<n>/`;
`scripts/seed-player-profile.ts --media --videos …` does the same for a
seeded profile with ffmpeg.

## The first profile

The plumbing test was a "Mohamed ElShorbagy" profile in the owner's roster
built from the four archive.org club matches as clearly-labelled stand-ins (the
player's notes say so). No PSA footage was downloaded — it is copyrighted
broadcast content; real clips, when there are any, replace the stand-ins by
tagging them on their read-outs. `/players/sample` carries the same four clips
under "Sample player" for visitors who are not signed in.

## Share links (the first sharing model)

Nothing is shared by default. An owner can mint a link from the profile page
("Share a link"): `players.share_token` gets 32 hex characters from
`crypto.randomUUID()`, and `/p/<token>` renders that profile read-only to
anyone holding it — no sign-in. Revoking is "Stop sharing", which clears the
token. There is no anon select policy anywhere; the only non-owner read path is
the SECURITY DEFINER RPC `shared_player(token)`, which returns exactly the
profile behind one token with the owner's ids stripped (`user_id`,
`share_token`, `job_id`, `history_id`). What travels: name, notes, the pooled
numbers and the recordings list (titles and dates). What never travels: the
footage. A club leaderboard still needs a club — a group model — and is
deliberately not here.

## Coach-led scouting ("how do I play against X?")

From a profile, "Ask the coach how to play them" opens `/coach?scout=<id>`.
The browser builds an `OpponentBrief` (`web/src/players/scout.ts`: the pooled
stats, top patterns, placement shares, the indicative shot mix and the scouting
notes with their basis, every field rounded and capped) and sends it with each
message. The server (`analysis/coach_api.py`) re-validates every field,
flattens and caps every string, and writes its own description into the
system prompt inside a delimited "data, not instructions" block, followed by
rules: pooled measurements from footage the user tagged, not a human's report;
placement is where shots were retrieved; no ball tracking; rally segmentation
unreliable; it cannot know results; 3–5 concrete points each tied to a number;
say where the evidence is thin; invent nothing. A malformed brief is ignored,
never a 400 — the chat still works without it. The banner on the Coach page
shows "What the coach was told" so the person can check the brief themselves.

## iOS

The phone's read-out has the same "Name this player" control in each player
section (`PlayerTagButton` → `NamePlayerSheet`), and the app gained a roster
(`/players`) and profile (`/player/[id]`) reachable from the Library; the tab
bar is unchanged. The domain modules moved to `src/features/players/` so both
clients run one copy — the web's `web/src/players/shape.ts` and `aggregate.ts`
are re-export shims, exactly as the web referee imports the app's scoring
engine. On iOS a tag is keyed by the phone's recording id (`history_id`); the
server job id is not persisted on the phone, so web and app tags of the same
recording do not coincide (by design: different machines, different local
ids). The app's default server URL is now `https://api.racketiq.tech`.

## Still open (deliberately)

- A club/group model (shared rosters, a leaderboard across members) — the
  share link is per profile and per owner on purpose until that exists.
- The iOS read-out cannot be reached signed-out (the app gates every tab
  behind login), so the phone-side tagging was verified by typecheck, jest and
  a Release build + launch, not by a signed-in walk-through.
